## What This Project Does (30 seconds)

OpsMemory AI is an **AI incident response agent that learns from its own failures**.

Most AI agents reset to zero every conversation. An SRE agent that forgets will recommend the same failed restart over and over. This one **remembers what it tried, what failed, and what actually fixed things** — then uses that memory to get better at responding to similar incidents.

**The demo proves:** Memory growth (0 → 41 facts), honest failure detection, and measurable improvement (34% faster on second incident).

## Key Technical Points

### 1. Memory Integration (Hindsight)

The project uses **Hindsight** as its memory layer. Three key calls:

- **`recall()`** before investigation — "Have we seen this before?"
- **`retain()`** after verification — Store the outcome (success or failure) with proof
- **`reflect()`** on demand — Query the whole history

**Critical design:** Failures are retained with equal weight to successes. The system stores "restart_service → verification_failed" as a first-class fact that can be retrieved later.

---

### 2. Honest Verification

Verification is **6 deterministic checks** over metrics before/after the action:

1. Primary signal improved (e.g., connection pool cleared)
2. Error rate normalized (< 5% threshold)
3. Underlying fault actually gone (not just symptoms hidden)
4. No new incidents opened
5. No anomalies in other services (collateral damage check)
6. Health score improved

**An LLM never decides if a fix worked.** Only metrics do.

When metrics don't normalize, verification says "FAILED" — and the failure goes into memory with proof attached.

---

### 3. Simulated vs Real

**What's simulated:**
- The infrastructure (8 microservices are simulated for reproducibility)
- The logs and metrics (generated by a causal fault simulator)

**What's real:**
- Detection algorithms (anomaly committee, log parsing)
- AI reasoning (real LLM tool-calling via OpenAI/Groq API)
- Memory layer (real Hindsight Cloud or local fallback)
- Verification checks (real metric analysis)
- The learning loop (real recall, real decisions based on memory)

**Why simulated data?** Reproducibility. Every demo shows the same learning arc. To connect real production logs, see `PRODUCTION_SETUP.md`.

---

### 4. The Learning Arc (What Makes This Convincing)

The learning loop is not scripted. Here's what actually happens:

1. **Incident 1:** AI has no memory of connection pool leaks
2. **AI recommends:** `restart_service` (the obvious first try)
3. **Simulator executes:** Restart clears connections but leak resumes
4. **Verification checks metrics:** Error rate still 8.2% (threshold 5%)
5. **Verification verdict:** FAILED (not scripted, determined by real metrics)
6. **Memory stores:** "restart_service failed on payment-service INCIDENT-xxx"
7. **Incident 2:** Similar connection pool leak
8. **AI recalls:** 8 memory hits including the previous failure
9. **AI reasoning:** "restart_service was attempted and failed, explicitly avoiding it"
10. **AI recommends:** `update_known_safe_configuration` instead
11. **Verification:** PASSED (metrics normalize)
12. **Result:** 31 tool calls vs 47 (34% faster)

**The key:** Step 5 is not scripted. The failure is real because the simulator has a causal model (restart doesn't fix leaks) and verification checks real simulated metrics.

## How to Verify It's Not Faked

**Concern: "How do I know the failure isn't scripted to always fail?"**

**Evidence:**
1. Check the verification code: `backend/app/domain/verification.py`
   - No hardcoded failures
   - Checks real metrics: `error_rate_normalized()`, `anomalies_cleared()`, etc.

2. Check the simulator: `backend/app/sim/engine.py`
   - Restart clears pool: `self._connections = self._max_connections`
   - But leak still active: Connections drain again
   - Verification sees this in metrics and fails

3. Run the learning loop multiple times:
   - Same failure happens every time (not random)
   - Proves it's causal, not scripted luck

4. Backend logs show real API calls:
   ```
   INFO: Calling Hindsight recall()
   INFO: Hindsight returned 8 hits
   INFO: AI reasoning includes citation to INCIDENT-xxx
   ```

5. Memory page shows facts you can read:
   - Click facts → See "restart_service failed on payment-service"
   - These are real stored memories, not UI tricks

## Common Questions

### Q: "Is this just a chatbot with a database?"

**A:** No. Key differences:

| Chatbot with database | OpsMemory AI |
|-----------------------|--------------|
| Stores conversations | Stores **verified outcomes** (success/failure with proof) |
| LLM decides what to remember | **Verification decides** what to remember |
| Memory is unstructured chat history | Memory is **structured facts** in Hindsight with relationships |
| No learning loop | Explicit **recall → reason → act → verify → retain** loop |
| Can't prove improvement | **Measurable improvement** (34% faster, quantified) |

---

### Q: "Why should I care about 34% improvement?"

**A:** Three reasons:

1. **It's measurable** — not subjective ("feels better"), but countable (47 → 31 tool calls)
2. **It compounds** — Every incident the AI resolves adds to memory, making future responses faster
3. **It's honest** — The 34% comes from avoiding a failed action that was actually tried and failed

Most "AI learns" demos show vague improvements. This one counts tool calls.

---

### Q: "What if I don't have OpenAI API key?"

**A:** The project runs without it! It falls back to:
- **Deterministic offline reasoner** (rule-based decision tree)
- **Local in-memory store** (instead of Hindsight Cloud)

The learning loop still works. You just won't see LLM reasoning in logs, and memory won't persist across restarts.

For full experience with real LLM: Get a free Groq API key (fast, free tier) and add to `.env`:
```
OPENAI_API_KEY=gsk_...
OPENAI_BASE_URL=https://api.groq.com/openai/v1
```

**A:** Four indicators:

4. **Real Hindsight integration:**
   - Not a mock — uses real Hindsight Cloud API
   - Memory persists across sessions
   - Can be self-hosted (Docker image available)
